# Browser layout cross-check

Validates Masharif's layout output against real browser (Chromium) rendering. For each
fixture there are two descriptions of the same layout — a `fixtures/*.html` page styled in CSS
and a tree built against the `masharif::Node` API — and both are reduced to the same
`{x, y, w, h}` per named node and diffed.

This exists because `tests-yoga/` (the vendored Facebook Yoga engine + its own test suite)
only gives ground truth for what Yoga itself does — it says nothing about Masharif's
`display:block`/`inline-block` normal-flow support, which has no Yoga equivalent at all. A
real browser is the only independent oracle for that, and it's also a useful second opinion
on the flexbox paths Yoga does cover.

## Two kinds of fixture

| | small fixtures | full-page fixtures |
|---|---|---|
| written as | a `Fixture_<name>` function in `harness.cpp` **and** a hand-matched `fixtures/<name>.html` | one spec tree in `pages/<file>.mjs` |
| C++ / HTML kept in sync by | you, by hand | `generate.mjs`, which emits both |
| good for | one property, 2–5 nodes | whole pages, 50–200 nodes |

Both end up in the same `harness.exe` and the same diff. The generated ones exist because
hand-syncing two ~100-node descriptions of one layout produces drift, and drift in this harness
reads as an engine bug.

## Prerequisites

- Node.js (any recent version) + npm
- Whatever C++ toolchain you already build Masharif with (this target — `browser_layout_harness`
  — is wired into the root `CMakeLists.txt`, so it builds the same way `unit_tests`/`example` do)

## Setup (one-time)

```sh
cd tools/browser_layout_check
npm install
npx playwright install chromium
```

## Running

One target does the whole pipeline — regenerate, build the harness, run it, extract the browser
ground truth, diff the two — each step cached/skipped when its own inputs haven't changed
(see `CMakeLists.txt` in this directory for exactly what's tracked):

```sh
cmake --build <your-build-dir> --target run_browser_layout_check
```

`<your-build-dir>` is whichever dir you already have configured against the root
`CMakeLists.txt` (CLion's, `cmake-build-debug-visual-studio`, wherever) — this target is
available there once, since `tools/browser_layout_check` is `add_subdirectory`'d from the
root. It's **not** part of the default `ALL` build (needs the one-time `npm install` above
done first, and shouldn't fire on an unrelated ordinary build), so build it by name.

Behind that one target, in order, only re-running what actually needs to:
1. `generated_cases.inc` / `generated_list.inc` — only regenerated if `generate.mjs` or a file
   in `pages/` changed. Also rewrites that spec's `fixtures/*.html`.
2. `browser_layout_harness` — a normal executable target; only relinks if `harness.cpp`, a
   generated `.inc`, or `masharifcore` changed.
3. `masharif_results.json` — only regenerated if the harness binary itself was rebuilt.
4. `web_results.json` — only regenerated if a fixture, `extract.mjs`, or a generated `.inc`
   changed (this is the expensive step — spins up headless Chromium — so it's the one most
   worth not repeating).
5. `compare.mjs` — always runs (it's a cheap diff), reading whichever of the two JSONs are
   current.

No CMake handy, or want a one-off build without touching your configured build dir? Compile
directly instead of step 2 — `harness.cpp` only needs `masharifcore`'s five `.cpp` files, no
CMake required (run `node generate.mjs` yourself first if you changed a spec):

```sh
clang++ -std=c++20 -O2 -I ../.. harness.cpp \
    ../../masharifcore/layout/FlexLayoutStrategy.cpp \
    ../../masharifcore/layout/LayoutStrategy.cpp \
    ../../masharifcore/layout/Node.cpp \
    ../../masharifcore/layout/NormalFlowStrategy.cpp \
    ../../masharifcore/structure/Style.cpp \
    -o harness.exe   # drop the .exe on non-Windows, or swap clang++ for g++/cl
```

The generated cases are long straight-line functions (the biggest builds a 203-node tree), so
expect this translation unit to take a few minutes at `-O2`. Drop to `-O0` if you are only
after the numbers — the harness does no work worth optimising.

`compare.mjs` prints a per-fixture roll-up plus every node that isn't a clean match, at a 0.6px
tolerance, and writes the full per-node table to `results.md`. `masharif_results.json`,
`web_results.json` and `results.md` are regenerated by every run and are not committed (see
`.gitignore`); the generated `.inc` files and `fixtures/*.html` **are** committed, so a reviewer
sees exactly what the harness compiles.

## Adding a small fixture

Add a `Fixture_<name>` function to `harness.cpp` (build a tree, call `N("id", ...)` for each
node you want reported, call `root->Calculate(W, H)`), register it in the `fixtures` vector
at the bottom of the file, and add a matching `fixtures/<name>.html` styled with the exact
same property values. Keep the same reset in every fixture
(`* { box-sizing: border-box; margin:0; padding:0; border: 0 solid transparent }`) so inline
per-element styles are the only source of truth, and always use flex-grow/shrink/basis
*longhand* properties rather than the `flex` shorthand (the shorthand resets flex-basis to
`0%`, not CSS's `auto` initial value, which Masharif's default matches).

`box-sizing: border-box` is not a style preference: an explicit `Px`/`Percent` size in the
engine *is* the border box (`Node.cpp:384`), so a content-box fixture would disagree with the
engine about every padded box.

## Adding a full-page case

Add a `pages/<something>.mjs` that default-exports one case (or an array of them):

```js
export default {
    name: 'page_thing',                 // snake_case: becomes Fixture_page_thing and page_thing.html
    title: 'Full page: ...',            // comment header in the generated C++
    calc: { w: 1280, h: 860 },          // available space passed to Calculate(); optional if the
                                        // root has an explicit px width and height
    root: { id: 'root', display: 'flex', /* ... */ children: [ /* ... */ ] },
};
```

Node fields: `id` (required, unique per case, root must be `root`), `display`
(`block`/`flex`/`inline-block`/`inline-flex`/`none`), `direction`, `wrap`, `justify`,
`alignItems`, `alignContent`, `gapRow`, `gapColumn`, `width`, `height`, `minWidth`, `minHeight`,
`maxWidth`, `maxHeight`, `margin`/`padding`/`border` (`{top,right,bottom,left}`), `position`,
`offsets`, `flexGrow`, `flexShrink`, `flexBasis`, `order`, `alignSelf`, `color` (cosmetic only),
`children`. Numbers are px, `'50%'` is a percentage, `'auto'` is the CSS keyword.

Then `node generate.mjs`. There is no text anywhere in these pages on purpose — the engine has
no text measurement, so a labelled AUTO-height box would diverge for a reason that has nothing
to do with layout. Give every box an explicit size or a flex basis.

### Authoring rules for generated cases

`generate.mjs` **validates** every spec against the rules below and refuses to emit anything
that trips one, naming the rule and the engine line responsible. They are not style
preferences — each marks a place where the engine and CSS answer different questions, so a
fixture that walks into one is not comparing the two engines on the same layout.

| rule | what it forbids | why |
|---|---|---|
| R4 | an inline-level box without an explicit width | AUTO width is a hardcoded 100px placeholder, not shrink-to-fit (`Node.cpp:602`) |
| R5 | padding/border on a container of inline-level children | `LayoutLine` starts its cursor at the border-box origin, not the content box (`NormalFlowStrategy.cpp:12-13`) |
| R6 | padding/border/margin-left/margin-top on an inline-level box in normal flow | line height double-counts padding and border; `LocalX`/`LocalY` are written before the leading margins are applied (`NormalFlowStrategy.cpp:14-21, 107-110`) |
| R7 | margin-top on a block-level child in normal flow | `LocalY` omits the child's own margin-top, and CSS additionally collapses adjacent sibling margins, which the engine does not model (`NormalFlowStrategy.cpp:95-99`) |
| R8 | padding-top/border-top on an AUTO-height block | `ApplyBlockAutoHeight` adds both on top of a child `LocalY` that already includes them (`Node.cpp:447-451`) |
| R9 | `position:relative` with offsets | `Style::Modify<T>()` cannot reach `PositionOffsets`, so a relative inset is silently a no-op (`Style.h:36-42`) |
| R11 | AUTO width + horizontal padding/border + a min/max-width clamp | the AUTO branches clamp the content box and then add padding; CSS border-box sizing clamps the border box (`Node.cpp:632-640`) |
| R12 | an absolute box with no positioned ancestor, or one whose containing block has padding/border | the engine anchors at the containing block's *content*-box origin and measures percentage insets against its *border* box; CSS uses the padding box for both (`Node.cpp:22-32, 216-218, 689-697`) |

Two of these are worked around structurally rather than avoided: an absolute overlay's
containing block is an unpadded positioned wrapper around the padded box (R12), and vertical
rhythm in normal flow is written as margin-**bottom** on the box above rather than margin-top on
the box below (R7). Both are how you write that layout such that the browser and the engine are
answering the same question.

Two more things `generate.mjs` states explicitly in the HTML because the engine's initial value
differs from CSS's, rather than leaving them implicit:

- `min-width:0; min-height:0` on every box. `Dimensions` defaults both to `0`
  (`Dimension.h:11-12`); CSS resolves `auto` on a flex item to a content-based floor, so every
  shrinking flex item would otherwise disagree.
- `vertical-align:top` on inline-level boxes and `font-size:0; line-height:0` on their
  container. The engine has no baseline or strut model: `LayoutLine` puts every box on the
  line's top edge and sizes the line from box heights alone. Inline-level siblings are also
  emitted with no whitespace between them, since collapsible source whitespace renders as a
  space the engine knows nothing about.

### Declared known gaps

`pages/gaps.mjs` holds one minimal fixture per rule that shapes a page: it walks straight into
the divergence, opts in with `allowGap: ['R7']`, and is declared in `compare.mjs`'s
`KNOWN_GAPS` with the engine line responsible. That way the rules above are pinned by tests
rather than only by prose, and a fix or a regression in any of those paths shows up.

If a declared gap starts matching, `compare.mjs` reports **GAP CLOSED** — that's the signal to
delete the case, the `KNOWN_GAPS` entry and the rule together.
